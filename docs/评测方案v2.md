# 市场 Agent 评测方案 v2（2026-11-12）

> 实施状态（2026-11-12）：判分器 v2、生成器 v2、参考解法校验、v1 结果重打分、试点已完成，结果见文末 §9 和进度记录 §2.13。dev_v2 之后的迭代和 test_v2 尚未开始。

## 0. 为什么要换

v1（formal_v1 100 题、holdout_v1 48 题）有三个结构性问题（详见进度记录 §2.11、§2.12）：

1. **只有端到端一个口径**。架构（ReAct / Plan-Execute / 反思）只影响"取数"这一段，而 8 成失败出在三者共用的报告环节，架构差别被淹没。
2. **题型偏短**。平均每题只需 1.1 组必需调用，规划和反思没有用武之地。
3. **样本少、单次运行**。48 题中有 23 题在不同配置间结果翻转，测不出 10 个百分点以内的差别。

另外，formal_v1 既用来开发又用来报告，已经被调过参。

## 1. 参考的做法（小红书、牛客、业界文章）

| 做法 | 来源 | 本项目怎么用 |

| 面试常问：评测集怎么来、Ground Truth 从哪来、多大；准确率上升是否代表更好；为什么有的任务做出来了 | 牛客淘天、Awaken 面经；小红书字节一面 | 方案里每个指标都写明口径、来源和样本量 |

## 2. 题集结构

### 2.1 三份数据，各管一件事

| 题集 | 用途 | 来源 | 规模 | 能否据此改代码 |
|---|---|---|---|---|
| dev_v2 | 日常迭代、调试 | 生成器，种子公开 | 约 150 题 | 可以 |
| regression | 防退化（发布门禁） | formal_v1 + holdout_v1 + fault_v1 原题 | 约 170 题 | 可以，但不能用来报告 |
| test_v2 | 对外报告 | 同一生成器，**代码冻结后**用新种子生成，并换一批日期窗口 | 约 180 题 | 不可以；改了代码就要重新生成 test_v3 |

参考答案沿用 v1 的做法：直接用 SQL、快照文件和政策原文计算，不经过智能体的工具。

### 2.2 两条维度交叉分层

**维度一：任务复杂度**（用来测架构差别）

| 层 | 定义 | 例子 | 预期谁占优 |
|---|---|---|---|
| L1 单跳 | 一次调用即可 | 某天某时段的电价 | 无差别（对照组） |
| L2 并行多取 | 几次互不依赖的调用 | 三个月均价比较；同比 | Plan-Execute 可一次规划完 |
| L3 依赖多跳 | 后一步参数来自前一步结果 | 先找最高价日，再查当天负荷；先定位最低价时段，再求风光合计 | ReAct 可以逐步推进；Plan-Execute 只能写死参数 |
| L4 长链路 | 5 步以上：拆分超过 32 天上限的区间、统计、检测、归因、政策 | 一个季度的负电价成因分析并引用当期规则 | 规划和反思应该占优 |
| L5 扰动 | 在 L2–L4 上注入工具失败、空结果、参数被拒 | 第一次 `explain_drivers` 失败 | 反思应该占优 |

**维度二：可答性**（用来测问题理解）

| 类 | 定义 | 正确行为 |
|---|---|---|
| A 可答 | 数据、时间都在覆盖范围内 | 给出数值 |
| B 部分可答 | 问题的一部分超出覆盖范围（如问全省气温，但只有济南） | 回答能答的部分，并说明缺什么 |
| C 不可答 | 地区、市场类型、时间、预测期超出数据目录 | 拒答并说明原因，不给数值 |
| D 需澄清或口径不定 | "最近"、"晚上 7 点"（时段边界）等 | 选一个合理口径作答，并写明口径 |
| E 版本冲突 | 政策跨修订版、生效日前后 | 引用当期有效版本，或分别说明 |

每格样本量：L1–L5 各 30–40 题，其中 A 类约占 6 成，B–E 类分布在各层。生成器按格子抽样，保证每格不少于 20 题，可以分格报告。

### 2.3 题目表述

- 模板题保证覆盖需求；每道模板题再由 LLM 改写成 1 种口语化说法（例如"昨晚那会儿电价高不高"），人工抽查 20% 确认语义未变，正式题集同时保留两种说法。
- 改写模型和被测模型不同家族，避免把被测模型的"舒适区说法"写进题目。

## 3. 指标：按链路分段

主指标只有一个：**任务通过率**（数值对、关键点齐、报告通过自检）。其余都是诊断指标，用于定位问题，不参与通过与否的判定。上游失败时，下游指标记为"跳过"，不重复计错。

| 阶段 | 指标 | 口径 | 主要回答什么问题 |
|---|---|---|---|
| 可答性 | 误答率、误拒率 | C 类给了数值算误答；A 类拒答算误拒 | 问题理解是否可靠 |
| 取数 | 证据到手率 | 工具阶段结束时，观测里是否已经包含参考答案对应的行和值（与报告无关） | **架构差别主要看这个** |
| 取数 | 必需调用召回、无效调用率、平均调用次数 | 沿用 v1 | 调用质量和效率 |
| 计算 | 数值归属正确率 | 报告里的数值，连同它所属的日期、时段、对象，都与参考行一致 | 张冠李戴 |
| 报告 | 该答未答率 | 证据已经到手，报告却没给出所问的量 | 过度保守 |
| 报告 | 自检误报率 | 人工抽查被自检拒掉的报告中，实际正确的比例 | 校验器是否误伤 |
| 解释 | 成因合理性（LLM 裁判，二元 Rubric） | 只用于成因类题目，裁判先与人工校准 | 归因质量 |
| 稳定性 | pass@1 均值、pass^3 | 每题 3 次运行 | 能力上限与稳定性 |
| 恢复 | 故障补救率 | L5 中注入的故障触发后，后续成功取到数的比例 | 反思是否起作用 |
| 成本 | token、调用次数、耗时（中位数和 P90） | 每次运行 | 性价比 |

另做两组**上界或分解实验**，把架构的贡献从报告环节里剥离出来：

- **Oracle 观测**：把参考答案所需的观测直接交给报告环节，测报告环节本身的上限。它和端到端的差距，就是取数阶段造成的损失。
- **固定报告器**：E0、E1、E2 取到的观测都交给同一个报告调用（温度 0），比较最终通过率，消除报告环节的随机性对架构比较的干扰。

## 4. 统计设计

- 每题每配置跑 3 次。题目层面取 3 次平均，用配对 bootstrap（按题重采样）给出差值的 95% 置信区间；二元结果附 McNemar 检验。
- 样本量按 v1 的经验估算：配置间不一致的题约占 19%。要在 80% 把握下测出 15 个百分点的差别，每层约需 65 题；测 10 个百分点约需 150 题。所以只在预期有差别的 L3–L5 上做架构比较，L1、L2 作对照，不追求显著。
- 先跑**试点**：L3、L4 各 15 题，E0 和 E2 各跑 3 次（180 次运行），实测不一致率和运行间方差，再定正式题量。
- 报告时写明样本量、运行次数、置信区间；不显著就写"未观察到差别"，不写"无效"。

## 5. 判分器

- 以代码判分为主：数值、日期、时段、调用参数、可答性标签都由程序对照参考答案判断。
- 新增**带来源的数值判分**：参考答案记录每个值所属的行键（日期、时段、对象），判分时要求报告中的值和行键都对上。这个判分只是评测侧的检查，不改智能体的校验器。
- LLM 裁判只用于"成因解释是否合理"：拆成 3–4 个二元 Rubric 条目，裁判模型和被测模型不同家族；人工标注 40 条，人机一致率达到 85% 以上才启用，之后每轮抽查 10%。
- 每道生成题自带一个参考解法（一组能拿到答案的工具调用）。题集生成后先用参考解法跑一遍，确认题目可解、判分器能判对；如果某题所有配置 3 次全错，先查题目，再查智能体（v1 的 XR02、XR06 就是这种情况）。

## 6. 防过拟合的流程

1. 开发期只看 dev_v2 和 regression，test_v2 尚未生成。
2. 每项改动事先写明针对哪种失败机制（见进度记录 §4 "通用改进方向"），用 dev_v2 上对应的诊断指标衡量效果，而不是看哪几道题由错变对。
3. 失败案例回流时，回流的是**生成器的模板或参数范围**（例如"依赖多跳"增加一种跳法），而不是把这道题本身加进题集。
4. 代码冻结后，用新种子和开发期没有用过的日期窗口生成 test_v2，只跑一次（每配置 3 次运行），结果直接写入报告。
5. 测试集跑完后若发现题目或判分错误，只改题目或判分，原样保留原始分数和勘误说明（与 holdout_v1 的处理一致）。

## 7. 实施步骤与成本估计

| 步骤 | 内容 | LLM 成本 |
|---|---|---|
| 1 | 生成器 v2：复杂度 × 可答性分层、参考解法、行键、口语改写 | 改写约几百次短调用 |
| 2 | 判分器 v2：分段指标、证据到手率、带来源的数值判分、跳过规则 | 无 |
| 3 | 用新判分器重新给 v1 结果打分（不重跑），验证分段指标能解释 §2.12 的结论 | 无 |
| 4 | 试点：L3、L4 各 15 题 × E0、E2 × 3 次 = 180 次运行 | 约 300 万 token，1–2 小时 |
| 5 | 按试点结果定题量，生成 dev_v2，按失败机制迭代（用户决定何时开始） | 视迭代次数而定 |
| 6 | 代码冻结 → 生成 test_v2（约 180 题）→ E0、E2 各 3 次，E1、E3 只在相关层各 1 次 | 约 1300 次运行，约 2300 万 token，按 v1 速度约 8–10 小时 |

成本按 holdout_v1 实测估算：每次运行平均约 1.7 万 token、76 秒，3 个并发约 140 次运行/小时。

## 8. 对项目经历的意义

- 能回答面试常问的问题：评测集怎么构建、Ground Truth 从哪来、多大；怎么证明某个模块有用（分层消融 + 置信区间）；怎么防过拟合（三份题集 + 冻结后生成）；指标上升是否代表更好（主指标 + 诊断指标 + 成本）。
- 架构结论按层报告，例如"在依赖多跳任务上 ReAct 比 Plan-Execute 高 X 个百分点，在长链路和扰动任务上反之"，比一个总体通过率更有说服力。

## 9. 实施结果（2026-11-12）

详细数字见进度记录 §2.13，这里只记录方案与实际做法的差异和据此作出的调整。

**与方案的差异**

- 口语改写没有用 LLM：没有不同家族的模型可用，改为每个模板写两种问法，其中一种口语化。生成的题目句式比真实用户的提问单一，正式报告时要说明这一点。
- 政策主题只有 rules_effective 一个同时出现在 dev 和 test 中，其余主题按 split 分开。
- LLM 裁判尚未启用，成因解释仍按 v1 的规则判分。
- 参考解法校验发现 2 题（并网细则施行日期，条款跨页）没有已知的工具路径能取到。这 2 题保留在集合中，单独标出，不删除。

**试点得出的调整**

1. 证据到手率可以作为诊断指标：在 v1 的三份结果上，它只在故障集上把各架构分开；在 dev_v2 的 L3 上，它把"取数"和"在结果里找对行"两类失败分开了（E2 证据到手 100%、通过 0%）。
2. 题量：L3 上每题配对差值的标准差为 0.37，测出 15 个百分点的差别每层约需 50 题（方案原估 65 题）。test_v2 的规模调整为 L3、L4、L5 每层约 50 题，L1、L2 各 20 题，可答性四类各 10–15 题，合计约 230 题。
3. L4 现在两种架构都接近 0%，处于地板效应，暂时不能用来比较架构。等 B 层（计划引用前一步结果、超长区间由工具层自动拆分）修好、通过率离开地板之后再看。
4. 成本按试点实测更新：每次运行约 2.9 万 token、约 120 秒，3 个并发约 90 次运行/小时。test_v2 只跑 E0、E2 各 3 次，约 1400 次运行、约 4000 万 token、约 16 小时；E1、E3 只在相关层各跑 1 次。
5. 下一步按方案 §6 的流程，在 dev_v2 上按失败机制迭代：先修 B 层和 C 层，再处理 A 层和 D 层。每项改动都用对应的诊断指标衡量（取错行率、L4 证据到手率、超限后完成整条链路的比例），不看单题对错。

**B、C 层修复之后（进度记录 §2.14）**

6. 试点中 E0 的数字被时间预算的计量错误压低：预算把限速排队算了进去，E0 在 L4 上 45/45 次被叫停。修复后，L4 已经离开地板（E0 84.4%、E2 57.8%），可以用来比较架构。评测记录里要保留 `rate_limit_wait_seconds` 和预算叫停事件，作为判断结果是否可信的检查项。
7. 修工具组之后，`required_calls` 的工具组按"能读到这张表的工具"定义，不按"某一个工具"定义。数据对不对由带行键的数值检查判断。test_v2 用同一个生成器生成，口径一致。
8. 证据到手后的失败里，有一部分来自智能体自身校验器的误报，不是模型错误。用新校验器离线回放已有报告，可以先估计一项校验器改动的效果和副作用，再决定花多少次运行去验证。
