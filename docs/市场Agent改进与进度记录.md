## 0. 先读这里：术语

| 术语 | 含义 |
|---|---|
| 智能体 / Agent | 接收自然语言问题，自己决定调用哪些工具、按什么顺序取数，最后写出报告的程序 |
| 工具 | 智能体能调用的确定性函数，如查电价、做预测、查政策。工具负责计算，LLM 负责决策和写报告 |
| E0 / E1 / E2 / E3 | 四种智能体结构，用来做对照实验。**E0** ReAct：走一步看一步，每次决定下一步调哪个工具。**E1** 规划 + 执行：先列完整计划再执行。**E2** 规划 + 执行 + 反思：执行后检查证据够不够，不够就重新规划（完整系统）。**E3** 在 E2 上去掉"政策生效区间过滤"，用来证明这个过滤有用 |
| as_of（截止时点） | 每个问题都假设站在某个历史时刻提问，智能体只能用这个时刻之前已经公开的数据，防止"偷看未来" |
| 数值绑定 | 报告里写出的每个数字都必须注明来自哪次工具调用返回结果的哪个位置，校验器会逐个核对 |
| 自检 / 校验器 | 报告写完后由代码检查：数字是否和证据一致、日期时刻是否对得上、政策是否在有效期内等。不通过就退回修改，最多两次 |
| pass@1 | 单次运行的通过率（多次运行时取平均） |
| pass^3 | 同一道题跑 3 次全部通过的比例，衡量稳定性 |
| 95% CI | 95% 置信区间。区间跨过 0 的差值，不能说两者有差别 |
| 配对比较 | 同一道题上比较两种结构，先对每题的多次运行取平均，再比较；比直接比总通过率更可靠 |
| L1–L5 | 题目复杂度分层。L1 单次查询；L2 两次独立查询；L3 后一步的参数要从前一步结果里取（如"最贵那天的负荷峰值"）；L4 五步以上的长链路；L5 在 L3/L4 题上注入一次工具故障 |
| A–E 可答性 | A 可答；B 部分可答（如问了山东和山西，只有山东的数据）；C 不可答（应拒答）；D 措辞含糊（要说明按什么口径答）；E 涉及政策版本（要引用当时有效的版本） |
| 开发集 / 测试集 | 开发集（dev）用来找问题、改代码；测试集（test）只在代码冻结后跑一次，用来报告最终结果。两者日期不重叠 |
| 冻结 | 正式评测前记录全部代码文件的哈希，之后改动任何文件，测试结果就不再对应这版代码，需要重新出题再测 |

## 1. 项目是什么

用户用中文提问，比如"2025 年 9 月 25 日电价最低的那一刻风光出力合计多少？""负电价最多的那个月里哪天最严重、为什么？"。智能体回答这类问题的流程是：

1. **判断能不能答**：把问题拆成要回答的几项，对照数据目录逐项判断可答、含糊或不可答。数据里没有的（如其他省份、日前价格）直接说明，不硬答。
2. **规划与取数**：调用 8 个工具查数据、做预测、找异常、分析供需原因、检索政策。
3. **反思**：检查证据够不够，不够就重新规划。
4. **写报告**：先逐项直接回答问题，再写异常、成因和政策依据，每个数字都绑定到证据。
5. **校验**：代码逐项核对，不通过就带着错误清单退回修改。

数据范围：山东电力现货市场 15 分钟实时数据 71,520 个时段（2024-01-01 — 2026-01-14），济南逐时气象 17,904 个点，17 份市场规则和政策文件。项目只做历史分析和历史时点的次日预测，不执行任何交易。

## 3. 最终结果

代码冻结后，用新的随机种子生成 237 道测试题（日期窗口与开发集完全不重叠，开发期间没人看过这些题），只跑一次。E0、E2 每题各跑 3 次，E1 只跑故障注入题，E3 只跑政策版本题。共 1484 次运行。

| 结构 | pass@1 | 95% CI | pass^3 |
|---|---|---|---|
| **E2 规划 + 反思（完整系统）** | **83.3%** | 80.3%–85.8% | 71.3% |
| E0 ReAct | 80.7% | 77.7%–83.5% | 66.7% |
| E1 无反思（仅故障题） | 34.0% | 22.4%–47.8% | — |
| E3 去掉生效区间过滤（仅政策版本题） | 33.3% | 13.8%–60.9% | — |

按复杂度分层（pass@1，E0 / E2）：

| 层 | 题数 | E0 | E2 | E2 比 E0 |
|---|---|---|---|---|
| L1 单次查询 | 49 | 95.2% | 92.5% | 无差别 |
| L2 两次查询 | 37 | 86.5% | 88.3% | 无差别 |
| L3 依赖前一步 | 50 | 88.0% | 86.7% | 无差别 |
| L4 长链路 | 51 | 75.2% | **83.7%** | **高 8.5 个百分点（95% CI +1.3～+15.7）** |
| L5 故障注入 | 50 | 60.7% | 66.7% | 高 6.0 个百分点，不显著 |

能得出的结论：

- **完整系统在没见过的题上通过率 83.3%**，同一题 3 次全过的比例 71.3%。
- **规划 + 反思的优势在长链路任务上**：L4 上比 ReAct 高 8.5 个百分点，统计上显著；简单题上两者没有差别。
- **反思让系统能从工具故障中恢复**：同一批故障题，有反思 66.7%，没有反思 34.0%，差 32.7 个百分点（95% CI +21.3～+44.0）。
- **不硬答**：30 次不可答问题全部正确拒答，36 次部分可答问题全部正确处理，没有一次误答或误拒。
- **数字不张冠李戴**：没有出现"字段对、行取错"的情况（把别的日期或时段的值说成所问的那一个），这是开发早期最主要的错误。

另外两项单独测过的指标：

- **电价预测**（测试期 2025-10-01 — 2026-01-14）：LightGBM 的平均绝对误差比最好的基线（"上周同时刻"）低 34.8%，每周重新训练后低 39.0%。但负价识别和尖峰预测不如基线，如实列出，不算成果（详细记录 §2.8）。
- **政策检索**（23 道政策题）：正确条款进入前 5 名的比例 95.7%，平均倒数排名（MRR）0.935。生效区间过滤把前 5 名里的失效版本从 38.3% 降到 0；去掉过滤后智能体的政策引用正确率从 91.3% 降到 21.7%（详细记录 §2.9）。

## 4. 改进历程

开发分为六个阶段。每个阶段的做法都一样：先用评测找出失败，按失败的**机制**（为什么错）归类，再做能覆盖一整类问题的修改，用对应的指标检验修改是否有效。不针对单道题打补丁。

### 阶段一：把系统跑通、跑稳（详细记录 §2.1–§2.3）

| 问题 | 改法 | 效果 |
|---|---|---|
| 模型默认开启"思考"，单次调用 19–45 秒 | 关闭思考模式 | 降到 3–20 秒 |
| 工具返回几千行数据，提示太长 | 只给模型压缩视图（前几行 + 每个字段的最大最小值及所在行），完整结果留给校验器 | 同类运行 token 从 10.9 万降到 2.7 万 |
| 模型会越过截止时点取数 | 截止时点由系统统一注入，工具层拒绝越界查询 | 杜绝"偷看未来" |
| 报告里的数字无法核对 | 引入数值绑定和校验器；计算得到的数（合计、差值、占比）单独声明计算方式，由校验器复算 | 每个数字都可追溯 |

### 阶段二：第一版评测，发现"开发集上的高分不可信"（详细记录 §2.5、§2.10–§2.12）

- 在 100 道开发题上，复杂任务完成率 85%。但这些题同时被用来找问题、改代码，等于在考题上复习。
- 另出 48 道新题（留出集，跑之前冻结），完成率只有 **60.4%**。
- 三种结构的完成率在两套题上都只差 1–2 题，**看不出规划有没有用**。

分析原因（详细记录 §2.12）：

1. 八成失败出在写报告阶段，三种结构共用同一套报告和校验，结构差别影响不到。
2. 题目太短，平均只需一组工具调用，规划用不上。
3. 两种结构各有一处短板，正好抵消：规划型只能把参数写死，多跳题第二步拿不到第一步的结果；ReAct 遇到查询长度上限后能拆分重查，没有反思的规划型不能。
4. 每题只跑一次，随机波动比结构差别大。

结论：不是规划没用，而是这套评测测不出差别。于是重新设计评测。

### 阶段三：评测 v2，能测出差别了（详细记录 §2.13，评测方案v2.md）

新评测的主要变化：

- 题目由模板加随机日期生成，按复杂度（L1–L5）和可答性（A–E）分层，开发集和测试集按季度交替取日期，互不重叠。
- 每道题自带一套能拿到答案的参考工具调用，生成后先验证题目可解、判分器能判对。
- 判分分阶段记录每次失败最早出在哪一步：中止 → 证据没取到 → 可答性判错 → 自检不过 → 该答的没答对 → 要点缺失。还单独统计"证据到手率"，把"取数没取到"和"取到了但报告写错"分开。
- 每题跑 3 次，用配对比较和置信区间判断差别。

在 30 道依赖多跳和长链路题上试点，结果是 ReAct 27.8%，规划 + 反思 **0%**。逐条核对后发现：规划型的证据其实全拿到了，但计划在第一步结果出来前就定死了，只能把整个月的数据拉回来，让模型在几千行里找值，结果取错行；长链路题第一步就撞上"单次查询最多 32 天"的上限，之后连锁失败。

### 阶段四：按失败机制修复（详细记录 §2.14）

在同一批 30 道开发题上做了四轮修复（fix1–fix4），每轮先归类失败、再改；前三轮各在这 30 题上重跑了一次，第四轮的改动在阶段五的抽查中一并验证。

| 失败机制 | 改法 |
|---|---|
| 时间预算把排队等待也算了进去，ReAct 在长链路题上 45/45 次被提前叫停（这是计量错误，不是模型行为） | 预算只计智能体自己的工作时间 |
| 规划器只能写死参数 | 计划里的参数可以写成"引用第 1 步结果里的某个值"，执行到那一步时再填入具体值 |
| 单次查询 32 天上限 | 新增汇总统计工具，一次可查 366 天，按日、月、时段分组，直接给出极值及其所在的日期时段 |
| 让模型在几千行里找最大值 | 工具直接返回"哪个分组最大、最小、有几组并列" |
| 字段对、行取错（如把 12:30 的风电值说成 10:00 的） | 校验器新增"行一致性"检查：陈述里写了日期或时刻，数值就必须来自那一天、那一时刻的行；按时段分组的结果附上时刻，模型能直接看出某行是几点 |
| 校验器把"2025年2月716个"误读成日期"2月71"，冤枉了正确报告 | 修正日期时刻识别；改动前先用新校验器离线重验已有报告，确认只消除误报、不放过错误 |
| 计划里参数格式不合法，到执行时才报错并连锁失败 | 规划阶段先按工具的参数规则检查，不合法就带着错误让模型重写 |

四轮下来，同一批题的通过率：

| | 修复前 | fix1 | fix2 | fix3 |
|---|---|---|---|---|
| E0 ReAct | 27.8% | 84.4% | 78.9% | 85.6% |
| E2 规划 + 反思 | 0% | 62.2% | 70.0% | 78.9% |

对应的机制指标：规划型取错行从 23/81 降到 0，超过 32 天上限的报错从几百次降到 0，依赖步骤连锁失败从 163 次降到 24 次。修复后两种结构在多跳题上的差距消失，说明修复前的巨大差距主要来自工具和计划表达能力的限制，而不是结构本身。

### 阶段五：可答性与报告结构（详细记录 §2.14 fix5）

扩大到所有题型抽查（10 个组别共 36 题）后，又发现三类问题：

| 问题 | 机制 | 改法 |
|---|---|---|
| 简单题报告是空的 | 报告里能放数字的只有"异常""成因"两栏，"某天最低价多少"这种直接答案没有位置，模型只写在不允许带数字的摘要里 | 报告第一栏改为"直接回答"，每个要回答的项对应一条，校验器逐项检查是否都答了 |
| 该拒答的硬答 | 没有先判断数据能不能回答，问山西电价就拿山东的数据冒充 | 取数前新增"可答性判断"一步，对照从数据库自动生成的数据目录，逐项判为可答、含糊或不可答 |
| 拒答题上程序崩溃 | 规划阶段的参数检查两次不通过时，错误没人接住 | 接住这个错误，交给执行和反思处理 |

同一批 36 题上，ReAct 从 27/36 升到 32/36，规划 + 反思从 26/36 升到 34/36；拒答、含糊、部分可答三类全部答对。

### 阶段六：冻结与正式评测（详细记录 §2.15）

冻结代码（记录 53 个文件的哈希），生成测试集，只跑一次，结果见第 3 节。

中间有一次作废：第一次冻结后生成的测试集（test_v2）刚开跑，就从开发集抽查中发现了空报告问题。当时决定停下修复。按规则，改了代码就不能再用这套题，所以 test_v2 连同已跑的 33 次结果一起作废删除（没有打分、没有看内容），修完后用新种子生成 test_v3。

## 5. 方法上的几点经验

- **评测先于优化**：第一版评测在开发题上 85%，换新题只有 60%。之后一直坚持开发集和测试集分开，测试集冻结后只跑一次。
- **按机制修，不按题修**：每次改动都写明针对哪类失败，用对应指标验证。例如"取错行"这一类，修复后取错行的指标从 23/81 降到 0，同时在没见过的测试题上也是 0。
- **校验器自己也会错**：两次发现校验器误报，冤枉了正确的报告。改校验器之前，先用新版本离线重验所有已存报告，确认只减少误报、不放过真错误。
- **不放宽标准**：模型写了数字却没标出处，就判失败，不为提分放宽校验。
- **计量要可信**：一次"ReAct 提前收尾"的结论，后来查出是时间预算把排队时间也算了进去，已在详细记录里更正。

## 6. 已知问题与后续方向

| 问题 | 影响 | 修法思路 |
|---|---|---|
| 运行中止时结果全丢 | 超出 token 预算或时间上限时整次运行报错退出，已取到的证据也不进报告。正式评测有 13 次因此失败（超时 8，全是政策版本题；超 token 4；报告格式两次不合 1） | 预算将尽时提前收尾、给报告预留份额；报告生成失败时由代码拼一份最小报告并标明未完成；无论成败都保存 trace。修完需重新冻结、出题再测（详细记录 §4） |
| 政策对比题弱 | 正式评测中规划 + 反思只过了 3/15 | 对比题需要分别检索两个版本，检索常只取到其中一版 |
| 模型漏标数字出处 | 自检拒绝是证据到手后失败的主因（规划 + 反思 50 次） | 从报告结构上减少需要模型自己标注的数字，例如更多计算放进工具 |
| 首次政策检索较慢 | 约 34 秒，主要耗在 CPU 上的重排模型；超时中止都和它有关 | 预加载模型，或把单次调用超时限制在剩余时间内 |
| 题目由模板生成 | 句式比真实用户的提问单一 | 有条件时用其他模型改写问法 |
