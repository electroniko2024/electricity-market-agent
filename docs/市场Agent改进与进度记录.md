## 2. 改进与优化记录

### 2.1 LLM 调用与预算

| 改进 | 效果 |
|---|---|
| 关闭思考：只发送 `thinking={"type":"disabled"}`（`ELLECTRIC_LLM_THINKING` 可改 `low/medium/high`，映射 `reasoning_effort`） | 单次调用由 19–45 s 降到 3–20 s，reasoning_tokens 由 700–4,000 降到 0。2026-11-09 实测：同时加 `reasoning_effort="none"` 会有 5/9 返回 HTTP 400，只发它则 4/9 仍在推理，所以不再附加 |
| 提示观测压缩：只给 LLM 压缩视图，完整结果留在 state/trace 供校验 | 同类运行 token 108,843 → 27,255 |
| 二级压缩：单条观测 > 8,000 字符或总量 > 30,000 字符时去掉数值范围、只留列表头 | 提示从 65–72k 字符降到约 32k，消除 45 s 超时 |
| 重规划预算守卫：token 或时间用掉一半后不再重规划；重规划无新步骤直接写报告 | 消除空转重规划，正常用例 0 次重规划 |
| 单次输出上限 `max_tokens=4000`；trace 记录 reasoning_token_count | 关思考是否生效可从 trace 直接核对；400 个任务 reasoning token 均为 0 |
| 限流：`ELLECTRIC_LLM_MAX_RPM`（评测脚本设 8）；HTTP 429 先等 15 s、再等 30 s 重试；trace 记录排队时长与重试次数 | 400 个任务 429 重试为 0 |
| 结构化输出纠错：schema 校验失败带错误重试一次；输出不是 JSON（Markdown 报告、截断）时按“非 JSON”专门提示重试，计入 `non_json_output_count` | 400 个任务中 24 次非 JSON 输出全部靠重试救回 |
| 总 token 预算 `MAX_TOTAL_TOKENS`：30,000 → 100,000 → **130,000**（2026-11-10，用户决定） | 400 个任务中 E3-C15 用了 113,453 token |

### 2.4 评测中发现并修复的校验器问题（2026-11-09 — 11-10）

这些都是校验器误判或表达能力不足，不是放宽标准；每项都有单测，值在证据里找不到的照样拒绝。

| 问题 | 修法 |
|---|---|
| 政策候选自带 `pol_…` 编号，模型照抄后被判“不存在的证据” | 产出时把 `pol_…` 映射回该检索观测的 `ev_…` 与候选位置；候选字段改名 `candidate_id` |
| `explain_drivers` 内嵌的政策候选（`/data/policy_evidence/data/evidence/i`）不被承认 | 校验接受嵌套位置，合格判断不变 |
| 计算得到的数（合计、差值、占比）无处绑定 | 新增 `derived_values`（sum / difference / ratio），校验用 operands 的证据值复算；ratio 为“其余 operands 之和 ÷ 最后一个”，以表达多段之和 ÷ 总数 |
| 绑定值按写出的小数位四舍五入（365.974 vs 365.974038690）被判不一致 | 允许按写出的小数位四舍五入一致 |
| 字段挂错观测（把 `explain_drivers` 的事件字段写到 `detect_anomaly` 名下） | 在所有观测中找“同名字段、同值”的位置自动改挂，并补 evidence_ids |
| 计数、序号、槽位区间被当成未绑定数值 | 计数等于所引用列表长度即算绑定；“第 N 段/号/时段”指向所引用条目时不算数值；`slot_id 0-6` 不再读成 -6 |
| 政策标题中的版本年份“（2023）”被当成 summary 数值 | 非数值陈述正则增加标题年份 |
| 压缩视图里的 `numeric_ranges.<字段>.count`、列表 `length` 在完整结果中没有对应字段，“有效时段个数”无法绑定 | 校验器识别 `<列表指针>/numeric_ranges/<字段>/count|min|max`（也接受漏写 `numeric_ranges` 段）与 `<列表指针>/length`，用完整列表现场重算后比对（2026-11-10） |
| 模型把 `known_limitations` 写成 `limitations`（照抄 `forecast_price` 输出的同名字段），提示词压不住 | 用户决定代码自动兼容：读到 `limitations` 合并进 `known_limitations` |

### 2.6 故障注入评测（2026-11-10，区分 E1 与 E2）

- 目的：正式集的题大多一次规划就能完成，反思没有用武之地，E1、E2 拉不开差距。故障注入题让关键工具第一次调用失败，专门看谁能补救。
- 做法：只在评测时注入（`ellectric/eval/market/faults.py`），题目里指定的工具第一次调用抛出“上游数据服务暂时不可用（连接超时）”，之后正常。题集 `fault_v1`（`build_fault_cases.py` 由 formal_v1 派生）共 20 题：从 E1、E2 在 formal_v1 中都完成的 C/E 题里选，问题、参考答案和判分要点不变，故障打在该题必需的工具上——C 类 `explain_drivers`、`detect_anomaly` 各 5 题，E 类 `forecast_price`、`explain_drivers` 各 5 题。
- 判分：沿用原定义，另加“故障后补救成功”（被注入故障的工具后来有一次成功调用）和“故障题完成率”。注入的失败照常计入无效调用，所以本题集的工具调用指标偏低，不和正式集比。

| 变体 | 故障后补救成功 | 故障题完成率 |
|---|---|---|
| E0（ReAct） | 25.0%（5/20） | 25.0%（5/20） |
| E1（无反思） | 0.0%（0/20） | 20.0%（4/20） |
| E2（完整） | **90.0%（18/20）** | **80.0%（16/20）** |

- 配对检验（McNemar）：E2 对 E1 是 13:1（p = 0.002），E2 对 E0 是 12:1（p = 0.003），**差异显著**；E0 对 E1 不显著（p = 1.0）。
- 更正（2026-11-12，§2.14）：E0 有 16/20 次是被时间预算叫停的，原因是预算把限速排队也算了进去。E0 的 25% 和"E2 对 E0"的比较因此不可靠；E2 对 E1 不受影响。
- E1 的 4 道“完成”题都是 E 类 `explain_drivers` 故障：缺一个“原因引用 explain_drivers”要点，覆盖率仍有 80%，按原定义算完成；E1 一次补救都没有。

### 2.9 政策检索指标 Recall@5 / MRR（2026-11-10）

- 口径：23 道需政策的题（D 类 15 + E 类 8），看必引条款在 `search_policy` 返回的前 5 条中的名次。命中规则同判分脚本：文件一致，且页码一致或关键词全部出现在摘录里。MRR 未命中记 0。“失效版本占比”= 前 5 条中在题目 `policy_at` 当天不生效的条数占比。
- 检索器本身（不经过智能体，查询词直接用题目原文）：

| 配置 | Recall@5 | MRR | 前 5 条中失效版本 |
|---|---|---|---|
| 生效区间过滤开（E0–E2 使用） | 95.7%（22/23） | 0.935 | 0.0%（0/115） |
| 生效区间过滤关（E3） | 95.7%（22/23） | 0.764 | 38.3%（44/115） |

- 智能体实际发出的检索（基于 formal_v1 记录）：

| 变体 | Recall@5（首次检索） | MRR（首次检索） | 前 5 条中失效版本 |
|---|---|---|---|
| E0 | 78.3%（18/23） | 0.645 | 13.6%（15/110） |
| E1 | 95.7%（22/23） | 0.870 | 0.0% |
| E2 | 95.7%（22/23） | 0.862 | 0.0% |
| E3 | 91.3%（21/23） | 0.634 | 37.4%（43/115） |

- 结论：过滤不影响能否检出必引条款（Recall 一样），但把失效版本从前 5 条中清掉，正确条款排名更靠前（MRR 0.764 → 0.935）。E3 政策引用完整率低（21.7%），正是因为失效版本混在候选里被模型引用。E0 的失效版本来自它传了与题目不符的 `policy_at`（有 1 题没有检索）。
- 分阶段消融（直接检索，同一索引、同一过滤与排序规则；最后一行与线上 `search_policy` 一致）：

| 阶段 | 过滤开 Recall@5 | 过滤开 MRR | 过滤开 Top1 | 过滤关 Recall@5 | 过滤关 MRR | 过滤关 Top1 |
|---|---|---|---|---|---|---|
| BM25 单路 | 95.7% | 0.685 | 10/23 | 82.6% | 0.457 | 4/23 |
| bge-m3 稠密单路 | 87.0% | 0.534 | 7/23 | 78.3% | 0.372 | 3/23 |
| RRF 融合（rerank 前） | 95.7% | 0.783 | 15/23 | 87.0% | 0.579 | 10/23 |
| RRF + bge-reranker-v2-m3（线上） | 95.7% | **0.935** | **21/23** | 95.7% | 0.764 | 14/23 |

- rerank 候选池（RRF 前 20 条）含必引条款：过滤开 23/23，过滤关 22/23。
- 结论：过滤开时 Recall@5 在 RRF 阶段就到顶了，rerank 的作用是排序：MRR 0.783 → 0.935，Top1 15 → 21。8 题名次变化中 7 题上升、1 题（D11）从第 1 降到第 2。过滤关时候选更杂，rerank 还把 Recall@5 从 87.0% 提到 95.7%。双路融合比任一单路都好（MRR 0.783 vs 0.685 / 0.534），稠密单路弱于 BM25，原因是政策条款术语密集，字面匹配占优。
- 计算脚本为离线一次性分析，不调用 LLM；直接检索需本地 Ollama bge-m3 与 reranker。

### 2.12 为什么 ReAct 和 Plan-Execute 没有差别（2026-11-12，离线分析，未改代码）

把每次失败按发生在哪个阶段拆开（工具阶段：必需调用不齐；报告阶段：工具都调对了，但报告自检失败、数值错或漏答）：

| 留出集 | 通过 | 工具阶段失败 | 报告阶段失败 | 中止 | 平均调用次数 |
|---|---|---|---|---|---|
| E0 ReAct | 30 | 3 | 15 | 0 | 1.7 |
| E1 Plan-Execute | 29 | 4 | 15 | 0 | 2.3 |
| E2 +反思 | 29 | 2 | 15 | 2 | 2.7 |

开发集上同样，E0/E1/E2 的报告阶段失败都是 6 次，工具阶段失败只有 E0 的 2 次（E13、E19）。

原因有四条，按影响大小排：

1. **瓶颈不在架构管的那一段**。E0–E2 只在"怎么调工具"上不同，写报告和校验用的是同一套。留出集上 8 成失败出在报告阶段，48 题里有 40 题三种架构都把必需工具调齐了，其中 9 题三者全挂。架构差别最多只能影响 2–4 题。
2. **题目太短，规划没有用武之地**。留出集平均每题只需要 1.1 组必需调用，E0 平均 1.7 次调用就够了。规划的价值在长链路任务上，这类题很少。
3. **两种架构各有一处结构性短板，正好抵消**。
   - Plan-Execute 的规划器只能写死参数。多跳题第二步要用第一步查出的日期，它只能把整月数据都拉回来，让写报告的模型在几千行里找值，结果找错（XM02 报了全月最大负荷而不是 8 月 25 日的；XM03 找错了最低价时段）。M 类 E0 3/5，E1/E2 都是 1/5。
   - 反过来，季度题撞 32 天上限时，E1 不能改计划，E2 靠反思、E0 靠逐步试探都能拆开重查（XH08、XH09）。
4. **样本少、单次运行噪声大**。48 题里有 23 题四个配置结果不一致，大多是报告阶段的随机翻转，和架构无关。E0 对 E2 只有 9 道不一致题。按配对检验粗算，要在 80% 把握下测出 10 个百分点的真实差别，大约需要 150 道配对题，或者每题跑 3 次。

结论：不是"规划没用"，而是这套评测在现在的系统上测不出架构差别。系统的短板在问题理解、取数粒度和报告环节，三种架构共用这几段。

3. **按 32 天切分而不是按自然月（C 层）**。题目问"每个月各多少"，智能体按 32 天一段去查，月度合计从未出现在观测里，报告给出的也是按段统计的数字。工具层若能自动拆分超长区间、提供按月分组，这一类失败可以整类消除。

**对正式题量的影响**：

- L3 上每题差值的标准差为 0.37（三次运行先取均值）。按 80% 把握、双侧 0.05 计算：测出 20 个百分点的差别每层约需 28 题，15 个百分点约 49 题，10 个百分点约 110 题。
- L4 现在两种架构都接近 0%（地板效应），无法比较架构。要等 B、C 两层修好、通过率离开地板后，L4 才有区分力；在那之前，把 L4 拿来比较架构没有意义。
- 建议：test_v2 的 L3、L4、L5 每层约 50 题，L1、L2 各 20 题作对照，加可答性四类各 10–15 题，合计约 230 题。E0、E2 各跑 3 次，约 1400 次运行、约 4000 万 token、约 16 小时。

**结论**：v2 题集能测出架构差别了，方向与 v1 的"无差别"相反：在依赖多跳任务上，ReAct 明显优于 Plan-Execute + 反思。结合 fault_v1（E2 在工具故障后的补救明显优于 E0），两种架构各有所长：反思擅长从单点故障中恢复，但写死参数的计划处理不了依赖关系。长链路任务目前两者都做不好，瓶颈在工具约束（32 天上限）和计划的表达能力，不在 LLM 本身。

**排查中发现的计量错误：时间预算把限速排队算了进去**

评测客户端限速 8 RPM，由 3 个并发共享，试点中 74–83% 的运行时间花在排队上。180 秒的运行时间预算把排队时间也算了进去：

1. **校验器把日期后紧跟的数当成日期的一部分（D 层，校验器误报）**。"2025年2月716个"被解析成日期"2月71"，剩下的"6"被当成未绑定数值；"15:00:00+08"中的秒和时区被当成数值"00""08"。两次修订后仍不通过，整份报告被自检拒绝。15 次自检拒绝中 9 次属于这一类，其中 6 次数值本来是对的。

5. **模型没有读压缩视图里的 `max_row`**：报告写"按日结果被压缩，只看到前 3 天，无法确定最多的一天"，其实 `numeric_ranges.negative_price_slots.max_row` 已经给出 2024-09-22。

- 校验器的日期、时刻识别：日期中的"日"必须带"日/号"或 ISO 分隔符，且日期的数字不能接着后面的数字（"2025年2月716个"中日期是"2025年2月"，716 是数值）；完整时间戳（`15:00:00+08`、`08:00+08:00`）整体识别为时刻。单独的"63号"仍按文号处理。

**运行中止时保留结果的修法（未实施）**

现状：token 预算或运行时间用完、报告连续两次不合 schema 时，`MarketAnalysisAgent.analyze` 抛出异常，评测把整次运行记为 aborted，trace 不保存，已经取到的证据也不进报告。test_v3 有 13 次是这样失败的（超时 8，全是政策版本题；超 token 4；报告不合 schema 1）。

修法分三层，原则是"降级完成，而不是整次丢弃"：

1. **预算检查改成提前收尾，不抛错**：规划、执行、反思、重规划每一步开始前检查剩余预算（token 和运行时间都算）。剩余不足以再做一轮取数时，不再调用工具，直接进入报告节点。给报告节点预留固定份额（比如总 token 的 15%、运行时间的 20%），保证它一定能运行。
2. **报告节点兜底**：报告生成本身失败（超时、截断、两次不合 schema）时，不抛错，由代码确定性地拼一份最小报告：`answers` 里能直接从观测中按绑定取到的值照常填，取不到的项写"未完成"；`unresolved_issues` 写明中止原因（如 `BUDGET_EXHAUSTED`、`REPORT_SCHEMA_FAILED`）；`verified=false`。这份报告同样走校验器，不放宽。
3. **trace 总是保存**：`analyze` 外层用 `try/finally` 写 trace，记录已执行的步骤、观测、中止原因和事件。评测里新增状态 `degraded`（降级完成），和 `aborted`（连 trace 都没有）分开统计；判分照常按报告内容判，降级报告里该答的数值缺失就判失败，不因为降级而放宽。

验证：用 token 上限压低到正常值一半的配置跑一批 L4/L5 开发题，检查 aborted 降到 0、每次都有 trace，以及降级报告的通过率。修完要重新冻结、生成 test_v4 再测。
