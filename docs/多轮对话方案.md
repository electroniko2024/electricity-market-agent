# 多轮对话与分档输出：设计与评测

> 面向第一次看这个项目的读者。单轮 Agent 的设计见 [README](../README.md)，评测框架见 [评测方案v2](评测方案v2.md)。

## 1. 要解决的问题

单轮 Agent 每次只接收一个完整的问题。用户在真实使用时会接着上一句追问：

- "那前一天呢？"（省略指标，改了日期）
- "那天全网负荷最高是多少？"（"那天"指上一轮答案里找到的日子）
- "这两天哪天贵，差多少？"（同时指前两轮的两个日期）
- "不对，我想问的是最低价。"（纠正上一轮）

另外，每个问题都输出一整份报告，太冗长。查一个数只需要一句话加出处；分析类问题要先给结论；只有用户要求时，才把整段对话合成一份报告。

## 2. 总体结构：给单轮 Agent 套一层外壳，Agent 本身不改

```
用户这一轮 ──► 要报告？──是──► 合并整个会话的报告
                 │否
                 ▼
          改写层（第一轮跳过）──► 要反问？──是──► 反问用户
                 │否：得到独立、完整的问题，并复述给用户
                 ▼
     单轮 Agent（原样）＋ 会话内工具结果缓存
                 ▼
          按复杂度分档展示（数字带出处标记）
```

单轮 Agent 的代码（`ellectric/llm/market_analysis.py`）在这一阶段没有修改，这样做有两个好处：

- **单轮的评测结论仍然有效。**
- **错误来源能分清。** 每道多轮题都同时用"标准独立问题"直接问一次单轮 Agent，得到上限。实际结果和上限的差距，就是改写层造成的损失。

代码在 `ellectric/conversation/`：

| 文件 | 作用 |
|---|---|
| `service.py` | 会话存储（每个会话一个 JSON 文件）和每一轮的流程 |
| `rewrite.py` | 把追问改写成独立问题，或决定反问 |
| `cache.py` | 会话内的工具结果缓存 |
| `presentation.py` | 分档展示和出处标记 |
| `session_report.py` | 整个会话的合并报告 |
| `periods.py` | 从文本里识别日期和月份，以及日历推算 |

## 3. 改写：模型提议，代码把关

模型读到的上下文是最近 4 轮已回答的"独立问题和简短答案"，不是完整报告，所以 token 不会随轮数膨胀。模型输出：

- 独立问题；
- 每个指代的候选对象；
- 每个继承或推算出来的值，推算要写明基准和偏移，例如"前一天" = 基准日期，偏移 -1 天。

模型的输出要经过代码检查才能用。这些检查都按机制设计，不针对某一道题：

1. **不允许编造日期。** 独立问题里出现的每个日期或月份必须满足下列之一，否则退回模型重写一次；仍不通过，就请用户把日期说完整：
   - 用户这句话里有；
   - 上文的问题或答案里有；
   - 是声明过的推算结果，由代码按"基准＋偏移"自己算，模型自己算出的值不采信；日期范围的两端按同一偏移推算；
   - 用户只说了月日，补上上下文里出现过的年份。
2. **有多个候选就必须反问。** 单数指代（如"那天"）有两个以上候选时，不管模型自己选了什么，都改为反问，系统不替用户猜。
3. **复数指代必须写全。** "这两天""它们"这类复数指代不需要反问，但所指的每个对象都必须出现在独立问题里。

改写结果会复述给用户（"我理解为：……"），理解错了，用户下一句纠正即可。

## 4. 复用已查过的证据

工具结果在会话内缓存，键是"截止时间 as_of、工具名、参数"三者组合：

- **命中时**返回结果的副本，Agent 把它当作普通观测记录，报告里数字绑定、行匹配、方向等校验照样执行。
- **as_of 不同就不复用**，避免信息泄露到另一个时间点。
- **只缓存成功的结果**，"暂不可用"这类可能是暂时性的失败不缓存。

## 5. 分档展示

后台分析和校验永远完整执行，分档只决定先展示什么：

| 档位 | 条件 | 展示 |
|---|---|---|
| 查数 | 问题拆出的每一项都要求数字或日期/时间（最多 3 项），且报告里没有成因和政策依据 | 一两句话，每个数字后面带出处标记 |
| 分析 | 其他情况 | 先给结论；逐项回答、异常、成因、政策依据都可以展开 |
| 报告 | 用户说"出个报告"之类 | 合并整段会话的报告 |

**出处标记**取自报告里已经通过校验的数值绑定：

- 数据：点开显示工具、参数、所在行（日期、时刻）、字段和取值；
- 政策：点开显示文件名、页码、生效期和条款原文。

所以标记只会指向 Agent 实际查到的东西。

**合并报告**的组织方式：

- 按主题（电价 / 负荷与新能源 / 天气 / 政策规则）组织各轮的直接回答；
- 同一次工具调用（同工具、同参数）只编一个号，引用过的所有取值都列在这个编号下面；
- 开头的概述由模型撰写，但不允许出现任何数字，因此不会带入未经校验的数值。

## 6. 接口

- `POST /conversations`：新建会话
- `POST /conversations/{id}/turns`：发一轮（SSE 流）。事件依次为 `rewrite`（复述或反问）、`agent_event`、`answer`（分档展示）或 `session_report`、`turn`、`done`
- `GET /conversations/{id}`：读取会话（不含工具原始结果）
- `GET /conversations/{id}/report.md`：合并报告的 Markdown

前端默认页就是"多轮对话"，原来的单次分析页保留。

## 7. 评测

### 7.1 题集

由 `ellectric/eval/market/build_dialogues.py` 生成：

- 每段对话 2–3 轮，日期取自与单轮题集相同的 dev/test 时间窗，dev 和 test 没有任何一天重合；
- 每一轮记录三样东西：
  - 期望行为：继续回答或反问；
  - 标准独立问题，以及它包含的日期和月份；
  - 一个单轮格式的题目，用现有的分段判分器（`score_v2`）判答案。

| 模板 | 考察点 |
|---|---|
| shift_day | 省略 + 前一天 |
| same_slot_prev_day | 时段和日期都继承，日期前移一天 |
| swap_metric | 同一天换指标（"那天""当天"） |
| found_entity | 指代上一轮答案里找到的日子 |
| next_month | 下个月 |
| last_year | 去年同期（日期范围） |
| correction | 纠正指标，保留日期 |
| topic_switch | 换话题：不得继承任何东西 |
| ambiguous | 上文有两个日期时说"那天"：必须反问 |
| cross_turn_compare | 三轮：分别问两天，再比较（应复用前两轮的证据） |

### 7.2 判分（`score_dialogues.py`）

- **反问轮**：系统反问、且没有运行分析，才算通过。
- **继续回答的轮次**同时满足三条才算通过：
  - 没有反问；
  - 独立问题里的日期和月份与标准答案完全一致（换话题时也就检查了没有误继承）；
  - 答案通过单轮判分。
- **汇总指标**：追问轮通过率、整段对话通过率、改写正确率、反问的召回和精确率、证据复用次数、每轮 token，以及上限（同一批追问直接问标准独立问题时的通过率）。
- **网络错误**：因 LLM 网络错误失败的对话不计分，要用 `--retry-network-errors` 重跑，规则与单轮评测一致。

### 7.3 dev 结果与据此做的修正

dev 集：40 段对话，84 轮。

| 轮次 | 追问轮通过 | 改写正确 | 反问召回 / 精确 | 上限 |
|---|---|---|---|---|
| 第一轮 | 84.1%（37/44） | 90.0% | 4/4 / 4/8 | 95.0% |
| 修正后第二轮 | 100%（44/44） | 100% | 4/4 / 4/4 | 95.0% |

第一轮的失败和据此做的修正，都是机制层面的改动，没有针对某一道题打补丁：

- **"去年同期"4 段全部被误判为反问。** 原因是日期范围的两端都推算了，但没有声明推算关系。修正：声明的推算可以以整个日期范围为基准；检查不通过时，退回给模型的提示里写明应该怎么声明。
- **"这两天"被当成歧义。** 修正：新增复数指代，所指对象必须全部写进独立问题。
- **"前一天同一时段"被误拒。** 原因是模型把基准日期填进了 value。修正：推算一律由代码按"基准＋偏移"计算，模型自己算的值不采信。
- **2 次 LLM 网络断开。** 修正：改为重跑，不计分。

第二轮的结果是在调过提示和检查的同一批题上得到的，只说明修正生效了，不能当作正式成绩。

### 7.4 正式结果（冻结后只跑一次）

- **冻结：** 代码哈希记录在 `cases/test_v4.freeze.json`（40 个文件）。
- **题集：** 冻结后用新种子生成 `multiturn_test_v1`，80 段对话、168 轮，日期与 dev 集不重叠。
- **运行：** 只跑一次。有 1 段对话因 LLM 网络错误重跑；上限对照里也有 2 段因网络错误重跑。

| 指标 | 结果 |
|---|---|
| 追问轮通过率（第 2 轮起） | **95.5%**（84/88），95% CI 89%–98% |
| 整段对话全部通过 | 95.0%（76/80） |
| 改写正确（日期/月份与标准完全一致） | 100%（80/80） |
| 追问答案通过（单轮判分） | 96.2%（77/80） |
| 上限：同一批追问直接问标准独立问题 | 97.5%（78/80） |
| 该反问时反问（召回） | 7/8 |
| 反问是否必要（精确） | 7/7，没有多余的反问 |
| 换话题时误继承 | 0/8 |
| 有证据复用的追问轮 | 13/80 |
| 每轮平均 token | 约 14,100 |

4 个失败的追问轮：

- **3 个是三轮比较题的第 3 轮，失败在单轮 Agent 的报告自检。** 其中 2 个是陈述里写了"96 个时段"却没有标出处，1 个是数值绑定到了陈述里没写的那一天。这与单轮 Agent 已知的"漏标数字出处"是同一类问题，不是改写造成的。改写在这 3 轮都是对的。上限对照里，同题 MT065 也是同样失败。
- **1 个是应该反问却没有反问**（上文有两个日期，用户问"当天负荷最大多少"）。模型只列了一个候选，所以代码的"多候选必须反问"规则没有触发。这个漏洞已经记入已知问题；修复思路是：遇到单数指代时，由代码根据上一轮自己数出候选日期，而不是依赖模型列出的候选。

结论：

- 改写层在测试集上没有造成可测量的损失。改写正确率 100%，追问答案通过率 96.2%，与上限 97.5% 基本持平。
- 剩下的损失来自单轮报告自检，以及一次漏反问。
- 题目由模板生成，句式比真实用户单一，这个结论只适用于题集覆盖的这些追问类型。
